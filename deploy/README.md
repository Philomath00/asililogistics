# Deploy Asili with HTTPS on Render

Render hosts the app; publishing the Codex cloud environment saves the development workspace. They are separate actions. No Render account, subscription, or deployment is created just by adding these files.

## 1. Connect Render to GitHub

1. Open [Render](https://dashboard.render.com/) and create an account using GitHub, or sign in.
2. Choose **New → Blueprint** and connect GitHub. Grant the Render GitHub app access to **Philomath00/asililogistics**. If the repository is missing, use GitHub's installed-app settings to add access; do not create or share a personal token.
3. Select that repository, branch **main**, and the root `render.yaml`. The service name is `asililogistics` (Render may require a unique name).
4. Review the **Starter** web service and **1 GB persistent disk** charges shown by Render before creating the resources. SQLite needs persistent storage; a free service with an ephemeral filesystem would lose deliveries. No billing action is performed from this repository.
5. Set the requested Meta values below, then click **Deploy Blueprint**. If you want to bring up the dashboard before connecting Meta, remove the four `sync: false` WhatsApp entries from the Blueprint in a separate deliberate change and add them later in Render's environment settings. Do not enter fake credentials.

Render's managed service provides an `https://…onrender.com` address and TLS certificate. The app uses Render's actual `RENDER_EXTERNAL_URL` for tracking links, so no hostname is invented in the source. Do not set `PUBLIC_BASE_URL` to localhost on Render. For a custom domain, configure it in Render, add the DNS records Render provides, wait for certificate validation, then set `PUBLIC_BASE_URL` to the custom HTTPS origin. Existing queued messages keep the original links.

The Blueprint creates `ADMIN_KEY` and `WHATSAPP_VERIFY_TOKEN` using Render's random-secret generator. In **service → Environment**, reveal the dispatcher key privately and enter it using **Dispatcher key** in the app. The local `.env` key is separate and is never uploaded to GitHub. Never paste keys into chat or logs.

## 2. Connect your existing Meta WhatsApp business app

In your Meta developers dashboard, open your existing business app and its WhatsApp API setup. The labels may vary by dashboard version.

1. Get the **Phone number ID** for the registered business number. A phone-number ID is not its international dialable number.
2. Use a properly scoped **system-user access token** for production, granted access to that WhatsApp Business Account/phone number. A temporary dashboard test token can expire. Sending needs `whatsapp_business_messaging`; management/setup operations can additionally require `whatsapp_business_management`. Do not expose the token to the browser.
3. Get the app's **App secret** from Meta app settings. This must be the secret for the app delivering webhook callbacks, not an arbitrary generated value.
4. Configure Render environment values:

| Name                         | Value/source                                         |
| ---------------------------- | ---------------------------------------------------- |
| `WHATSAPP_ACCESS_TOKEN`      | Authorized Meta token, entered as a secret           |
| `WHATSAPP_PHONE_NUMBER_ID`   | Registered phone number ID                           |
| `WHATSAPP_APP_SECRET`        | Actual Meta app secret, entered as a secret          |
| `WHATSAPP_TEMPLATE_NAME`     | Approved utility template name                       |
| `WHATSAPP_TEMPLATE_LANGUAGE` | Template language code, default `en`                 |
| `WHATSAPP_VERIFY_TOKEN`      | Already generated by the Blueprint; reuse it in Meta |

Create/approve a utility template with three **body** text parameters in this exact order: delivery ID, status, full tracking URL. Example body:

```text
Asili delivery {{1}}: {{2}}. Track your delivery: {{3}}
```

In Meta Webhooks/WhatsApp Configuration, configure:

- Callback URL: your real Render/custom HTTPS origin followed by `/webhooks/whatsapp`.
- Verify token: the `WHATSAPP_VERIFY_TOKEN` generated in Render.
- Subscribe to `messages` and ensure the app is subscribed to the WhatsApp Business Account. Configure production business/number verification as required by Meta. For Meta's test number, register the recipient in the allowed test recipient list.

Keep app credentials in **Render** for the deployed backend. Adding credentials only to Codex does not add them to Render. A proxy-injected Codex token may work only for outgoing HTTPS calls to Meta; a placeholder is not usable as a local HMAC app secret. The webhook app secret and dispatcher key require actual server-side secret environment values in the host.

## 3. Verify the deployed integration

Run `npm run verify:live` from a trusted checkout or private Render shell with the real `PUBLIC_BASE_URL` set to the deployed HTTPS origin. All required names are in `.env.example`. The script prints results, never credential values. It checks HTTPS, dispatcher access control, webhook verification, valid/invalid signatures, and read-only Meta phone-number access. It does **not** prove real message delivery without the next step. Local TLS verification is retained; do not disable it.

For a real send:

1. Obtain consent from a test recipient you control. Create a delivery using that number, or set sender and customer to that same test number to queue only one message per status.
2. Review `/api/messages` through an authenticated local script/browser or the outbox to select a pending message ID. Do not use real customers as test targets.
3. In the trusted deployment shell set these additional variables securely:
   `ALLOW_LIVE_WHATSAPP_SEND=1`, `WHATSAPP_LIVE_MESSAGE_ID` to that message ID, and `WHATSAPP_TEST_RECIPIENT` to the exact opted-in international number.
4. Run `npm run verify:live -- --send`. This sends exactly the selected existing outbox message, and waits up to 30 seconds for Meta's delivered/read webhook. A success response from Meta alone is not treated as delivery proof. A timeout is a failed delivery check; inspect the outbox/Meta rather than blindly resending.
5. Open the rider link on a real phone over HTTPS, allow location permission, keep the page open, and confirm GPS movement on the customer's page. Complete pickup/transit/delivery and send the corresponding updates. Headless GPS simulation does not replace this physical-phone check.

The network policy now permits `graph.facebook.com` and `tile.openstreetmap.org`. If OpenStreetMap denies tiles at its provider layer, adding the hostname again will not fix the problem. The app sends only its origin as referrer to meet map policy without leaking private URL tokens. A deployed public origin must still comply with OpenStreetMap's usage policy; select a supported tile service for production volume rather than bypassing a provider block.

## Alternative: your own server with Caddy

The repository also includes a Docker image, Compose configuration and `deploy/Caddyfile` for a server you control. Point a domain's A/AAAA records to it, allow inbound ports 80/443, install Docker/Compose, and run:

```sh
npm run setup:secrets
# Edit ignored .env securely: add ASILI_DOMAIN, TLS_EMAIL and real Meta values.
docker compose config --quiet
docker compose up -d --build
```

Caddy obtains a publicly trusted certificate and redirects HTTP to HTTPS. Certificate issuance requires reachable DNS/ports; a local container test does not establish public hosting. Persistent volumes retain the SQLite database and TLS state. Do not run `docker compose down -v` unless you intend to delete data. Schedule consistent SQLite backups and test restore. Only run a single app instance per SQLite database.
